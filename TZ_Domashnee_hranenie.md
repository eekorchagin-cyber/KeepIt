# Проект технического задания «Домашнее хранение»

Версия 0.2 от 11.10.2026. Статус: проект для обсуждения и оценки разработки.

## 1. Назначение и результат

Разработать семейную программу для учёта домашних вещей, их фактического расположения и запасов расходных материалов. Программа должна работать с iPhone и в браузере компьютера, предоставляя членам семьи доступ к одной общей базе данных.

Основные задачи:

- Найти вещь по названию, категории, характеристикам или метке места хранения.
- Последовательно описать содержимое комнаты, шкафа, полки или коробки, предварительно отсканировав её метку телефоном.
- Отслеживать перемещение, выдачу и возврат долговечных вещей.
- Учитывать поступление, расход и остатки материалов, формировать список пополнения.
- Печатать описи одной коробки и целого помещения с разбивкой по вложенным местам.
- Согласованно работать нескольким членам семьи с разных устройств.

## 2. Платформы и архитектура

### 2.1. Предлагаемое решение

Адаптивное веб-приложение с возможностью добавления на главный экран iPhone (PWA). Одна программа обслуживает мобильный и настольный интерфейсы. Отдельное приложение App Store для первой версии не требуется.

Центральный сервер хранит общую базу и фотографии. iPhone, компьютер и телефон другого члена семьи обращаются к этому серверу по HTTPS. На устройствах хранится локальная рабочая копия доступных данных и очередь несинхронизированных операций. В целевой версии сервер является источником подтверждённых общих данных; локальные изменения сохраняются и при отсутствии связи.

Для базы предлагается PostgreSQL; фотографии хранятся в управляемом сервером файловом хранилище с привязкой к записям базы. Конкретный стек разработчик предлагает при оценке, сохраняя требования настоящего ТЗ.

### 2.2. Размещение и выбор архитектуры

Рабочая версия размещается на внешнем интернет-ресурсе с постоянным HTTPS-адресом и доступна из любого места с телефонов, планшетов и компьютеров. Каталог семьи закрыт авторизацией; наличие интернет-адреса не означает публичного доступа к данным.

Предпочтителен простой и недорогой способ размещения, соответствующий архитектуре. При оценке учитывать не только разработку, но и оплату хостинга, сопровождение, резервное копирование, восстановление и дальнейшие обновления.

| Этап / вариант | Назначение и условия |
|---|---|
| Статическое PWA, например размещённое на GitHub Pages | Возможный вариант минимального прототипа с локальными данными и ручным обменом файлами. Данные семьи и секреты не включать в публикуемые файлы приложения |
| Веб-приложение с внешней общей базой и серверной частью | Целевая версия с автоматической синхронизацией, семейными учётными записями и серверной проверкой прав |
| Статический интерфейс и отдельный сервис данных | Допустимая альтернатива, если она упрощает эксплуатацию и обеспечивает все требования безопасности и синхронизации |

Публикация одного интерфейса сама по себе не обеспечивает общую базу. Конкретные возможности, тарифы и ограничения выбранного хостинга проверить перед согласованием архитектуры. Домашний сервер не является базовым вариантом нового проекта; его можно рассматривать только как отдельно согласованную альтернативу.

На первом этапе допустима ручная синхронизация «экспорт → передача файла → импорт и объединение». Это временный режим прототипа: данные на другом устройстве обновляются после импорта. Целевая версия должна автоматически синхронизировать общую семейную базу.

Если разработчик видит более простое решение, он сначала предлагает его заказчику и объясняет преимущества, ограничения и последствия для эксплуатации. Не усложнять архитектуру и интерфейс без необходимости.

### 2.3. Совместимость

Обязательные проверки: Safari на iPhone, запуск с главного экрана iPhone, Safari и Chrome на macOS, Chrome и Edge на Windows. На старте разработки зафиксировать конкретные поддерживаемые версии и реальные устройства для приёмки. Минимальная ширина мобильного интерфейса — 375 CSS-пикселей.

Доступ к камере организовать по HTTPS с доверенным сертификатом и разрешением пользователя. Предусмотреть ручной ввод кода и выбор места из дерева при отказе в доступе к камере. Распознавание меток должно работать в поддерживаемом Safari и не зависеть исключительно от наличия одного встроенного API браузера.

## 3. Пользователи и семейный доступ

| Роль | Возможности |
|---|---|
| Администратор семьи | Все операции; создание и отключение пользователей, управление справочниками, настройками и резервными копиями |
| Участник | Просмотр, поиск, добавление и изменение вещей, операции с остатками, перемещения, инвентаризация, печать |
| Наблюдатель | Просмотр, поиск и печать без изменения данных |

Каждый человек использует отдельную учётную запись. В истории фиксируются автор и время операции. Администратор выдаёт одноразовое приглашение с ограниченным сроком действия и может отозвать доступ. Общий пароль на всю семью не использовать.

Первая версия — одна семейная база, общая видимость данных для всех её пользователей согласно роли. Разграничение видимости отдельных документов и комнат — отдельное расширение.

## 4. Структура мест хранения

### 4.1. Исходное дерево

| Объект | Помещения / зоны |
|---|---|
| Дом | Коридор; кабинет; средняя комната; спальня; прачечная; ванная; зал; балкон; лоджия |
| Дача | Дом; барбекю; баня; металлический гараж; каменный гараж |
| Работа | Кабинет; комната отдыха |

Балкон и лоджия — разные места. Название «Дом» внутри «Дачи» обозначает дачный дом.

Ниже размещаются шкафы, стеллажи, полки, ящики, коробки и другие контейнеры. Допускаются пропуск уровней и вложенные коробки. Вещь можно хранить непосредственно в помещении, например газонокосилку в гараже.

### 4.2. Карточка места

Обязательные данные: неизменяемый внутренний идентификатор, уникальный читаемый код, название, тип и родительское место, кроме корневого объекта. Дополнительные данные: фотография, описание расположения, примечание, дата последней инвентаризации.

Пример пути: Дача → Каменный гараж → Стеллаж № 1 → Полка № 2 → Коробка «Электрика». Пример не означает установленного расположения вещей пользователя.

Требования:

- Добавление, переименование, перемещение и архивирование мест.
- Запрет циклов: нельзя поместить коробку внутрь самой себя или её потомка.
- При перемещении коробки всё содержимое меняет полный путь автоматически; идентификаторы и метки сохраняются.
- Перемещение контейнера записывается в историю, по которой можно восстановить прежний путь содержимого.
- Запрет удаления непустого места без предварительного перемещения или архивирования содержимого.
- Раздельный показ вещей непосредственно в месте и вещей во вложенных местах; отсутствие двойного подсчёта.

## 5. Штрихкодирование и работа с камерой

### 5.1. Формат меток

Основной формат — QR-код как двумерный штрихкод, удобный для камеры телефона. Дополнительно обеспечить печать и распознавание Code 128 с коротким уникальным кодом места.

QR-код содержит ссылку на карточку места с неизменяемым идентификатором. Code 128 содержит уникальный код, который приложение разрешает в карточку. Ни один код не содержит пароли, токены доступа или опись имущества. Сканирование не отменяет авторизацию: после входа пользователь попадает в выбранное место.

На этикетке печатаются: QR-код или Code 128, короткий читаемый код, название места. Полный путь — необязательный, так как он меняется при переносе коробки. Изменение названия и расположения не должно требовать переклейки кода. При смене домена сервера необходимо сохранить старый адрес через перенаправление либо организовать перепечать QR-этикеток.

### 5.2. Создание и печать

Поддержать создание метки одного места, пакетное создание меток и предварительную печать свободных меток. При первом сканировании свободной метки авторизованный участник задаёт название, тип и родителя. Привязка выполняется один раз; повторное сканирование открывает существующую карточку.

Шаблоны: A4 с настраиваемой сеткой этикеток и отдельная этикетка, например 50 × 30 мм. Предусмотреть настройку полей и масштаба 100%, контрастную чёрно-белую печать, свободную зону вокруг кода. Проверять читаемость на реальном принтере и iPhone. Повторная печать сохраняет тот же идентификатор.

### 5.3. Описание содержимого после сканирования

1. Пользователь нажимает «Сканировать место» и наводит камеру на метку.
2. Программа показывает название, фотографию при наличии и полный путь места.
3. Пользователь выбирает «Добавить вещь», «Добавить расходный материал» или «Проверить содержимое».
4. При добавлении место уже заполнено; его название остаётся видимым на экране.
5. После сохранения форма позволяет добавить следующую позицию в то же место.
6. Для перехода к другой коробке пользователь сканирует новую метку; незавершённый ввод предлагается сохранить или отменить.

Повторное распознавание одного кода в видеопотоке не создаёт дубликаты. Неизвестный или чужой код не открывает произвольные ссылки автоматически; предлагаются понятное сообщение и разрешённые действия.

Заводской штрихкод товара, если указан, помогает выбрать номенклатуру; он не является уникальной меткой места или экземпляра. Внешняя база товаров для первой версии не требуется.

## 6. Каталог, категории и карточки

Категория описывает вид вещи, а режим учёта — способ работы с ней. Они независимы: в категории «Канцелярия» могут быть долговечный степлер и расходная бумага.

Начальные категории: книги; электроника; документы; лекарства; канцелярия; одежда; обувь; материалы для творчества; инструменты; оборудование; расходные материалы; расходные материалы для сада. Верхняя одежда — подкатегория одежды; электрические инструменты — подкатегория инструментов; удобрения — подкатегория садовых расходников.

Категории, подкатегории, синонимы и дополнительные теги редактируются. «Электротехника» может использоваться как общий тег для электроники, электрических инструментов и оборудования.

Общие поля: идентификатор, название, категория, подкатегория, режим учёта, фотографии, описание, теги, модель или марка, характеристики, единица измерения, примечание. Место и количество задаются на уровне экземпляра либо остатка в конкретном месте.

Минимум для быстрого ввода: название, режим учёта, категория и место; для расходника также количество и единица. Неизвестное количество нельзя автоматически считать одной единицей.

Исходные 19 позиций дачного каталога загрузить как заготовки, без вымышленных остатков и точных мест:

| Позиции | Предварительный режим |
|---|---|
| Разводной ключ; набор гаечных ключей; дрель; шуруповёрт; болгарка; шлифовальная машина; рубанок; электрический паяльник; комплект инструментов электрика; электрофен | Долговечные вещи |
| Снегоуборочная машина; газонокосилка | Долговечные вещи |
| Электролампочки; фильтры; клей; термостойкий клей для печи | Расходные материалы |
| Удобрение для газона; удобрение для растений; универсальное удобрение | Расходные материалы |

Заготовки имеют отметку «Требует заполнения» и не участвуют в остатках и покупках до ввода фактических данных. Тип рубанка, назначение электрофена и возможные два отдельных паяльника требуют уточнения. Различные модели фильтров, цоколи ламп и составы удобрений учитываются разными позициями.

## 7. Учёт долговечных вещей

Основной режим — отдельная карточка экземпляра: одна дрель, одна книга, один комплект инструментов. Экземпляр имеет уникальный идентификатор, количество 1 и одно текущее местоположение. Групповой количественный учёт одинаковых долговечных предметов допускается с возможностью выделения отдельных экземпляров без увеличения общего количества.

Состояние (исправен / требует ремонта / неисправен) учитывать отдельно от доступности (на месте / используется / передан / не найден / списан).

Операции:

- Добавить и сфотографировать вещь.
- Переместить: выбрать вещь и отсканировать новое место, подтвердить перенос.
- Взять в использование: указать пользователя; сохранить постоянное место возврата.
- Передать другому человеку: указать кому, дату и необязательный срок возврата.
- Вернуть: отсканировать фактическое место возврата; восстановить доступность.
- Отметить ремонт, потерю или списание с причиной; сохранить историю.

Использование вещи не уменьшает её количество и не формирует заявку на закупку автоматически. Для выданной вещи показывать «У пользователя …», а домашний адрес хранения обозначать как место возврата, не как подтверждённое фактическое расположение.

Комплект учитывается либо одной карточкой, либо карточкой комплекта со связанными компонентами. Компоненты не должны одновременно считаться независимыми дополнительными комплектами. В первой версии достаточно карточки комплекта и текстового перечня состава; отдельное движение компонентов — расширение.

## 8. Учёт расходных материалов

### 8.1. Остатки и операции

Одна номенклатурная позиция может иметь остатки в нескольких местах и партиях. Для партии при необходимости указать дату поступления, срок годности, дату вскрытия. Материалы с разными единицами или несовместимыми характеристиками не объединять автоматически.

Операции: поступление; расход; перемещение; списание по порче или сроку; корректировка по инвентаризации. Каждая операция содержит количество, единицу, место, автора, время и основание. Остаток вычисляется по подтверждённым операциям.

Перемещение создаёт связанное уменьшение в исходном месте и увеличение в новом в одной транзакции. Общий запас семьи не меняется. Отрицательные остатки запрещены. Ошибка исправляется обратной операцией с объяснением, а не бесследным удалением истории.

Количество допускает дроби для массы и объёма и только целые значения для неделимых штук. Точность хранить десятичным типом. «Упаковка» переводится в базовую единицу только по указанному пользователем коэффициенту: например, упаковка удобрения = 2 кг. Не складывать килограммы, литры и упаковки без явного преобразования.

Примеры: было 5 ламп, использована 1 — осталось 4; было 2 кг удобрения, израсходовано 0,3 кг — осталось 1,7 кг. Установка лампы или фильтра считается расходом со склада; учёт установленного оборудования — необязательное расширение.

### 8.2. Пополнение и список покупок

Для позиции и выбранной области контроля (вся семья или конкретный объект «Дом / Дача / Работа») задаются минимальный и целевой остатки. Целевой остаток не меньше минимального. Для одной позиции не создавать одновременно перекрывающиеся автоматические правила семьи и её объектов.

Доступный запас — пригодные к использованию остатки в области контроля; просроченные и явно заблокированные партии исключаются. Неизвестный срок годности не считать просроченным, но помечать как неизвестный.

Если доступный запас меньше или равен минимуму, создать или обновить одну активную строку пополнения. Предлагаемое количество = максимум из 0 и разницы между целевым и доступным запасом за вычетом уже подтверждённого ожидаемого поступления. Довести результат до целой закупочной упаковки, если задан её размер.

Пример: минимум 2 лампы, цель 6, доступно 1, ожидается 2 — предложить ещё 3 лампы. Ожидаемое поступление не увеличивает фактический остаток до приёмки.

Показать запас в других объектах и предложить перенос вместо покупки, когда это возможно. Повторное обновление не создаёт дублей. Пользователь может изменить количество покупки и добавить позицию вручную.

Статусы: требуется; запланировано; заказано; получено; отменено. «Получено» открывает форму фактического поступления с количеством и местом. Частичное получение допустимо; остаток заказа сохраняется. Одновременная приёмка с двух телефонов не должна удвоить приход.

### 8.3. Отчёт по расходованию

За выбранный период показывать отдельно: начальный остаток, поступления, расход, списания, перемещения внутрь и наружу, корректировки и конечный остаток. В общем отчёте семьи внутренние перемещения не считаются расходом. Отдельный отчёт «Требует пополнения» включает область контроля, доступный остаток, минимум, цель, ожидаемое поступление и количество к покупке.

## 9. Поиск

Единая строка поиска доступна с главного экрана. Искать по названию и его части, категории и подкатегории, тегам, модели, описанию и коду. Обеспечить нечувствительность к регистру и эквивалентность «е / ё». Предусмотреть редактируемые синонимы: «болгарка / УШМ», «электротехника», «удобрения».

Фильтры: объект, помещение и вложенные места, тип учёта, категория, состояние, доступность, наличие остатка, необходимость пополнения, срок годности. Поиск по родительской категории включает подкатегории.

Результат показывает фото, название, тип, полный путь и статус; для расходника — количество по каждому месту и общий итог в одной единице. Выданные вещи показываются с получателем и местом возврата. Черновики выводятся отдельно от подтверждённого наличия.

## 10. Инвентаризация

После сканирования места пользователь запускает проверку только его непосредственного содержимого либо всего поддерева. Программа фиксирует состав на начало проверки и позволяет отметить наличие вещей, уточнить фактический остаток, добавить найденное и отметить ненайденное.

Перед завершением показать расхождения. Отсутствие отметки не означает автоматическое списание. Корректировки остатков подтверждаются отдельно и записываются в журнал.

При параллельном изменении проверяемых вещей или остатков после начала проверки система предупреждает о конфликте и требует сверки актуальных данных. Завершение не должно перезаписывать более новые движения.

## 12. Несколько устройств, синхронизация и отсутствие связи

### 12.1. Распределение данных

Один опубликованный экземпляр приложения доступен по постоянному адресу с нескольких устройств, без установки отдельных сборок.

| Данные | Где хранятся и как используются |
|---|---|
| Места, вещи, категории, пользовательские справочники, фотографии, движения, покупки и история | Общие данные семьи; в целевой версии хранятся на сервере и синхронизируются с устройствами согласно правам |
| Настройки вида, размер шрифта, последнее открытое место, разрешение камеры | Локальные настройки конкретного устройства; не перезаписывают настройки других устройств |
| Рабочая копия каталога и загруженные фотографии | Локальные данные для автономной работы; явно указывается время последней синхронизации |
| Новые записи, изменения, фотографии и операции без сети | Сохраняются локально до подтверждённой передачи; отображаются как ожидающие синхронизации |
| Учётные записи и права | Общие серверные данные; управление требует связи и проверки полномочий |

До реализации согласовать состав автономно доступных данных и фотографий. Отсутствующие в локальной копии сведения не представлять как отсутствующие в общей базе.

### 12.2. Работа без интернета

После первого успешного запуска и подготовки локальной копии потеря интернета не должна приводить к пустому экрану, сбою или потере введённых данных. Предусмотреть повторный запуск без сети, просмотр и поиск загруженного каталога, добавление и изменение вещей, перемещения и регистрацию расхода.

Изменения сохраняются в постоянном локальном хранилище и остаются после закрытия приложения. Статусы различаются: «Сохранено на устройстве», «Ожидает синхронизации», «Синхронизировано», «Требуется разрешить конфликт». Показывать режим связи, время последнего обмена и число ожидающих операций.

Сканирование внутри приложения должно находить ранее загруженные места без сети. Для неизвестной метки показывать возможность ручного ввода или повторной проверки после восстановления связи. Первоначальная загрузка приложения, вход нового пользователя, получение отсутствующих данных и управление доступом требуют интернета.

Фотографии, ещё не переданные на сервер, сохранять локально и отправлять при восстановлении связи. При нехватке места или ошибке локального сохранения сообщать об этом явно; не показывать успешное сохранение.

Автоматическую отправку выполнять при открытом приложении и восстановлении сети, а также при следующем запуске; предусмотреть кнопку «Синхронизировать». Не полагаться исключительно на работу приложения в фоне.

### 12.3. Ручная синхронизация прототипа

Экспорт содержит идентификатор семейной базы, версию формата, устойчивые идентификаторы записей и операций, их версии, сведения об удалении и необходимые вложения. Передача файла выполняется пользователем самостоятельно.

Импорт сначала проверяет формат и принадлежность базе, затем показывает новые записи, изменения и конфликты. Перед объединением создаётся локальная резервная копия. Совпадение названий не является основанием объединять разные вещи.

Повторный импорт одного файла не создаёт дубликатов и не повторяет приход или расход. Удалённые записи не восстанавливаются незаметно из старого файла. Несовместимый формат отклоняется с понятным объяснением. Конфликтующие изменения показываются пользователю для выбора; молчаливая замена всей базы запрещена.

### 12.4. Автоматическая синхронизация и конфликты

В целевой версии подтверждённые сервером изменения отображаются на других открытых устройствах не позднее чем через 5 секунд при стабильной связи. После возвращения из фона данные обновляются. Локальные очереди отправляются с повторными попытками без дублирования.

Изменения карточек контролируются по версии записи. При конкурирующих изменениях показываются обе версии и авторы; пользователь выбирает итог. Для совместимых независимых изменений допускается безопасное автоматическое объединение с сохранением истории. Конфликты перемещения одной вещи, изменения родителя коробки, удаления и редактирования требуют явного разрешения.

Операции с остатками выполняются атомарно и имеют уникальные идентификаторы. Повторная отправка не повторяет движение. Остатки синхронизируются через операции, а не заменой итогового числа.

Если два устройства расходуют по 2 единицы из общего остатка 3, сервер подтверждает только допустимую операцию; вторую сохраняет как конфликтную до сверки. В автономном режиме остаток является предварительным: без связи нельзя гарантировать, что другой участник не израсходовал тот же запас. Подтверждённый отрицательный остаток запрещён. Пользователь видит подтверждённый остаток и влияние ожидающих операций раздельно.

Синхронизация не заменяет резервное копирование. При переходе от ручного режима к общей базе сохранить идентификаторы, историю и пользовательские справочники, исключив повторное применение операций.

## 13. Безопасность, сохранность и эксплуатация

- Авторизация для всех карточек, фотографий, API, выгрузок и печатных документов; QR-ссылка не предоставляет самостоятельного доступа.
- HTTPS, безопасное хранение паролей, ограничение перебора, защищённые сессии и возможность отключить потерянное устройство.
- Серверная проверка прав на каждую операцию и объект; защита от подмены идентификатора.
- Фотографии обрабатывать без обязательной отправки в сторонние сервисы; удалять геометки EXIF при загрузке.
- Файлы проверять по типу и размеру; размеры и допустимые форматы описать в документации.
- Не подключать обязательную внешнюю аналитику, распознавание или рекламные сервисы.
- Для общей базы вести журнал изменений и операций с остатками.
- Ежедневная автоматическая резервная копия базы и фотографий, отдельная от рабочего сервера; хранить 30 ежедневных копий с контролем успешности.
- Шифрование резервных копий; ключ восстановления хранится у администратора отдельно.
- Целевые показатели: потеря данных при аварии не более 24 часов; восстановление не более 4 часов при наличии исправного сервера и копии. Проверить восстановление до приёмки.
- Перед выходом при наличии несинхронизированных данных предложить синхронизацию или резервный экспорт; удаление таких данных допускается только после явного подтверждения. Затем очистить локальные данные пользователя. Ранее скачанные файлы автоматически удалить невозможно. Отзыв доступа блокирует последующие серверные запросы; удалённое мгновенное стирание копии на отключённом устройстве не гарантируется.

## 17. Порядок разработки и комплект поставки

3. **Общая семейная база.** Учётные записи, автоматическая синхронизация, очередь автономных операций, разрешение конфликтов, серверная проверка прав и резервное копирование.
4. **Постепенное расширение.** Выдача и возврат, партии и сроки, пополнение, печать описей, Code 128, инвентаризация и остальные требования. Порядок небольших выпусков согласовывать по приоритетам.
5. **Эксплуатационная приёмка.** Проверить все обязательные сценарии, восстановление резервной копии, публикацию, обновление предыдущей версии и пилот в одном помещении.

После каждого изменения проверять новый сценарий и ранее работающие функции: запуск, создание и поиск, сохранение и повторное открытие, сканирование, расход, импорт или синхронизацию — по составу текущего выпуска. Проверки фиксировать в кратком протоколе. Новые функции не считаются готовыми при поломке ранее согласованных.

Передать исходный код, инструкции пользователя, публикации, обновления, резервного копирования и восстановления, описание данных и миграций, начальные справочники и протокол испытаний. Секреты передавать отдельно. Сроки и стоимость определяются после оценки.

За пределами согласованного базового объёма: автоматическое распознавание предметов по фото, внешние каталоги товаров, интеграции магазинов, отдельное приложение App Store, индивидуальные права на комнаты и сложный покомпонентный учёт наборов.

## 20. Публикация, доступ и безопасное обновление

### 20.1. Постоянный адрес и установка

После создания и согласования рабочей версии предусмотреть её размещение на выбранном внешнем ресурсе с постоянным HTTPS-адресом. Один адрес используется на телефонах, планшетах и компьютерах. На поддерживаемых устройствах приложение реализуется как PWA: пользователь добавляет его через «На экран Домой» и запускает как самостоятельное приложение. Обычный браузерный запуск остаётся доступным.

Не требовать отдельных сборок для членов семьи и переустановки после каждого выпуска. Выбор конкретного сервиса согласовать с заказчиком; публикация и доступ к семейным данным — отдельные настройки.

### 20.2. Версии, кэш и данные

Каждый выпуск получает номер версии и краткое описание изменений. Версию приложения и состояние обновления можно посмотреть в настройках. Формат базы и экспортных файлов версионируется отдельно.

Новую версию публиковать по прежнему адресу. Обновление кода не удаляет вещи, фотографии, историю, остатки, настройки, локальную очередь и пользовательские справочники.

Предусмотреть управляемое обновление кэша PWA: загрузить и проверить новый комплект файлов, уведомить пользователя, завершить или сохранить текущий ввод и только затем активировать обновление. Не смешивать файлы разных выпусков и не удалять рабочую автономную версию до готовности новой. При следующем запуске с сетью проверять наличие обновления и сообщать о неудаче.

Изменение структуры данных выполнять проверенными миграциями. До миграции создавать резервную копию; при ошибке сохранять исходные данные и предлагать восстановление. Старый клиент с несовместимым форматом не должен портить серверные данные: требуется понятное предложение обновиться с сохранением локальной очереди.

Подготовить порядок возврата к предыдущему выпуску с учётом совместимости базы. Переход между хостингами должен сохранять данные и по возможности постоянный адрес, включая работоспособность напечатанных QR-кодов.

### 20.3. Проверка перед каждым выпуском

Перед публикацией проверить:

- основной сценарий: выбрать или отсканировать место → добавить вещь → найти её;
- сохранение после закрытия и повторного запуска;
- приход, расход и отсутствие повторного списания;
- мобильный интерфейс, камеру и запуск с домашнего экрана;
- отключение сети, автономный повторный запуск и восстановление связи;
- импорт с объединением либо автоматическую синхронизацию на нескольких устройствах;
- обновление именно предыдущей установленной версии с накопленными данными, настройками, справочниками и несинхронизированными операциями;
- резервное копирование и предусмотренный для выпуска способ восстановления.

Публиковать выпуск после успешной проверки применимых сценариев; сохранять протокол и возможность восстановления.

### 20.4. Пошаговая помощь заказчику при публикации

После завершения разработки предоставить инструкцию по выбранному ресурсу, включая необходимые учётные записи, настройки адреса, HTTPS, базы и резервных копий. При сопровождении выполнять **по одному действию за раз**: дать конкретный шаг, дождаться подтверждения заказчика, затем перейти к следующему. Не считать шаг выполненным без подтверждения.

После публикации отдельно пройти проверку строго по цепочке:

**Веб-адрес → запуск в браузере → установка на телефон → запуск с домашнего экрана → сохранение данных → обновление версии → работа со второго устройства → синхронизация данных.**

По каждому пункту фиксировать результат; при ошибке устранить её и повторить проверку.
